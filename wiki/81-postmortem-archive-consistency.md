# 档案一致性复盘

## 现象与根因

1. 保存配额失败后内存已更新，磁盘仍是旧值，界面没有统一未保存状态。Zustand 的 set 先更改内存，再调用 persist；异常不能证明状态未变。
2. 合法 JSON 的 `sessions:null` 进入合并后，partialize/UI 再次抛错；错误恢复微任务也会触发 persist。仅捕获 JSON.parse 不等于验证档案。
3. 多窗口各持旧副本，整体覆盖可丢记录。异步逐次等锁又使“立即刷新”与保存完成之间出现窗口。
4. 新输出的非空 focus 被套到旧档案，拦住了可以安全显示的历史值。读兼容与写契约需要不同强度。

## 本轮纠正

在读取进入 merge 前校验 envelope 与结构，失败保护原字节；运行时保存状态不入档案。写失败保留内存/旧文件，提示下载和重试；按字节预算，不静默丢 200 场以后的记录。现代浏览器在 hydrate 前获取窗口级写权限，之后同步写；另一窗口可读、提示未保存并可导出。无锁平台保留字节冲突检测。

恢复先预览、下载当前档案，再合并或替换；同 ID 不同内容拒绝选择。主档案与 3D 是不同键，逐项恢复并检查失败，不宣称跨键原子事务。

## 教训与证据

要分别测试读、写、合法坏结构、配额、并发和页面离开；不能以启动恢复通过推出全链路安全。Node 24 也提供 navigator.locks，浏览器能力检测必须同时确认真实 DOM，避免服务器/测试替身持有浏览器式长锁。新模型输出缺字段应失败/修复，历史安全空值应继续可读。
