## R1｜共享预算、生成资格与健康检查分离失效

**现象与影响。** 2026-10-07 21:54 北京时间只读核对：当日保守预留已使用 1,998,465，日池 2,000,000，剩余 1,535，活动请求为 0。前后两次 `GET /api/health?retry=1` 均 HTTP 200、`available`；其间正式 3D 生成 HTTP 429、`modelIssue: quota`。没有修改计数，也没有证据表明供应商钱包余额不足。

**根因。** [`shared-budget.ts:26`](../../app/src/lib/shared-budget.ts#L26) 按 `3 × (UTF-8 字节数 + 4096 + maxTokens)` 预留，包括 SDK 重试；结束只释放并发位，不结算实际用量。即使没有输入，文字/3D 短任务也分别需要至少 17,688/17,388，已超过剩余额度。八次约 20 KB 输入、7,000 输出上限的复盘调用可预留 746,304；这是上界计算，不是实测账单。

[`server-model-health.ts:8`](../../app/src/lib/server-model-health.ts#L8) 的重新检查清掉运行时观察，只读取模型元数据。应用共享池、供应商余额均归为 `quota`，再由 [`model-copy.ts:18`](../../app/src/lib/model-copy.ts#L18) 告诉用户“补充额度”，造成重复检查和错误操作方向。单进程观察缓存也不能代表两平台所有实例。

**建议。** 保留原子全局上限；区分共享日池、共享并发位、供应商余额/限流、网络及配置错误。免费检查返回元数据可访问、当前生成资格和预算来源，避免把元数据成功标成所有任务可生成。明确日池重置时间（UTC 日界，本部署北京 08:00）与个人模型路径。后续再设计幂等预留/结算：有可靠 usage 时结算，没有 usage、取消或重试未知时保守扣留；不能直接取消上限或简单全额退款。

**验收。** 两平台实例同时探测；低于最小任务预留、池尚有余量但长任务不够、并发满、真实供应商 429、取消/重试未知用量均给出不同且准确的状态。检查不消耗生成额度，用户原话保持可恢复。

证据：[预算观察](../../docs/reviews/whole-repo-2026-10-07/budget-observation.json)、[前后健康与生成](../../docs/reviews/whole-repo-2026-10-07/health-and-generation.json)。此项续接 10-06 backlog，不算新的额度事故根因。

## R2｜3D 跨标签写入会静默覆盖

**实际复现。** A 写“标签 A 的旧草稿”，B 打开同一场景并写“标签 B 的新草稿，应该保留”。磁盘读回 B 新值。A 只切换第一/第三人称，磁盘变回 A 旧值，而 B 页面仍显示新值。B 在仍打开时刷新有机会被离页刷新保存救回；因此不能声称所有刷新都丢失。但关闭 B 后，再让 A 切视角，新标签实际恢复的就是 A 旧值，B 新草稿已经丢失。

**根因。** [`DinnerApp.tsx:45`](../../app/src/features/dinner/DinnerApp.tsx#L45) 初次读取后保存在各窗口内存；[`DinnerApp.tsx:179`](../../app/src/features/dinner/DinnerApp.tsx#L179) 每次保存整个存档。没有对应的跨窗口版本比较/所有权校验。文字档案的 [`archive-storage.ts`](../../app/src/store/archive-storage.ts) 已有 Web Locks 与写前比较，未覆盖独立 3D 键。整个存档都被写回，转录和场景进度也存在相同覆盖机制；本轮直接证明的是草稿丢失。顶部文字档案冲突提示存在，但未阻止独立 3D 存档写入。

**建议。** 为 3D 键补写入所有权与版本冲突处理；旧窗口先保留内存进度和下载入口，阻止继续覆盖。复用主档案的保护原则，但保持 3D schema 与密钥存储分离。切视角、房间动画等展示状态不能携带过期对话整体覆盖最新记录。

**验收。** 双标签交替输入、关闭其中一页、旧页切视角/移动、刷新、导入 3D 备份；同时测无 Web Locks 回退。确认最新原话/草稿不被覆盖，冲突有可操作提示。

证据：[逐步读回](../../docs/reviews/whole-repo-2026-10-07/browser-observations.json)、[新标签现场页面（草稿值见逐步读回）](../../docs/reviews/whole-repo-2026-10-07/draft-loss.png)。

## R3｜删除密钥后可被旧窗口重新写回

**实际复现。** 使用 `enabled: false`、`synthetic-old-audit-key`，无真实凭证。设置页所在标签先取得主档案写权限，随后打开第二个 3D 标签。第一页通过实际“清除所有数据”确认按钮清除，立即读回 `socialcoach.llm.v1 = null`；第二页打开“更多 → 接入模型”，该键重现，包含旧虚构密钥。

**根因。** [`byok.ts:53`](../../app/src/lib/byok.ts#L53) 使用默认持久化，没有跨标签失效监听；`openSheet`、`closeSheet` 的瞬时 UI 状态变更也触发持久化写回配置白名单。另一页 [`settings/page.tsx:342`](../../app/src/app/settings/page.tsx#L342) 仅清除当前 store 和设备键，旧页仍持有凭证。主档案锁不能保护这份独立配置。

**建议。** 给清除操作增加跨标签失效/删除版本；保存配置前核验当前设备版本。瞬时 UI 状态与持久配置写入分开；接收删除后旧页清空凭证和模型状态、终止相关待发操作。继续保持密钥独立、不进入备份。

**验收。** 清除后旧页开/关弹窗、切语言、保存旧草稿均不能复活密钥；旧配置不可再用于请求。仅使用虚构凭证。单窗口清除、跨窗口更新、导出不带密钥一起回归。

证据：[实际清除步骤与读回](../../docs/reviews/whole-repo-2026-10-07/browser-observations.json)、[旧窗口配置截图](../../docs/reviews/whole-repo-2026-10-07/credential-reset.png)。证明的是删除语义失效，没有发现密钥发往第三方的证据。

## R4｜损坏 3D 原件阻断健康档案恢复

[`dinnerBackup()`](../../app/src/features/dinner/storage.ts#L4) 有意将坏 JSON 原字节保留为 `{ unreadable: raw }`。但 [`decodeBackup():18`](../../app/src/lib/backup.ts#L18) 对 `dinner3d` 直接使用 `SaveSchema`，失败就抛出 `backup-dinner`。一份合法主档案单独导入可恢复 1 场；加上自身导出的 unreadable 包装后，整个导入被拒绝。界面设计的“主档案成功后再单独恢复 3D”根本走不到。

**建议。** 独立解析主档案与 3D；健康主档案允许预览/恢复，坏 3D 原件隔离、解释并提供原样下载。不得默默丢弃坏字节，也不得恢复不合法的 3D 数据。

**验收。** 自身导出文件往返：无 3D、健康 3D、损坏 JSON 包装、合法 JSON 坏 schema；健康主档案仍可恢复，坏 3D 留有原件。保留版本和同 ID 冲突的严格检查。

证据：[恢复结果](../../docs/reviews/whole-repo-2026-10-07/backup-results.jsonl)、[最小重放](../../docs/reviews/whole-repo-2026-10-07/reproduce-backup.ts)。

## R5｜最新续聊评分可能被最近八次窗口排除

[`proficiency.ts:9`](../../app/src/lib/proficiency.ts#L9) 先按时间排序，再倒序以 Map 按 `practiceId` 去重。Map 更新已有键的值不会移动插入位置，所以“较早练习的最新续聊快照”仍排在该练习第一次出现的位置。之后每项最多八次观察，可把真正最新的高评分排除。

反例：A 旧评分 0，其后八场独立评分 0，最后 A 续聊评分 3。现有公式结果 `communication = 1.3`；按最新独立观察正确取样应为 `1.7`。3D [`buildDinnerReview():65`](../../app/src/features/dinner/lib/review.ts#L65) 在新复盘快照用当前时间，保留 practice 身份，这条路径可触发问题。

**建议。** 先选每个 practice 的最新有效快照，再对去重后的值排序，最后取每项八次；保留中性先验和引文验证，不重设计评分公式。

**验收。** 跨八次边界的旧 practice 新评分、相同时间、旧版无 practiceId、多个技能的覆盖窗口；重复快照仍只算一次。

证据：[数值结果](../../docs/reviews/whole-repo-2026-10-07/algorithm-results.jsonl)。重放是只包含函数所读取字段的最小反例，未宣称其为完整 API/schema 档案。

## R6｜私有模拟备注直接进入公共界面

[`prompts.ts:175`](../../app/src/lib/prompts.ts#L175) 要求 `meta.note` 为中性舞台提示，禁止教练判断。但 [`roleplay-output.ts:53`](../../app/src/lib/roleplay-output.ts#L53) 只限制字符串长度，完整校验仍原样返回；[`Chat.tsx:255`](../../app/src/components/practice/Chat.tsx#L255) 接受并在 575 行显示。

反例使用既有“拒绝临时加班”场景：NPC 台词没有揭示底牌，`revealed:false`、`disclosures:[]`，备注却写出“其实客户只要先看前三页”，再无引文地评价用户“表现很差”；完整输出校验接受了它。此底牌与场景私有内容一致。证明公共投影没有覆盖备注，不是证明当前 Ling 在线泄漏了底牌。

**建议。** 取消自由文本公开备注，或只从已公开台词/有限动作生成中性状态。不要把另一次昂贵模型“审查备注”当作必需修复，也不要用几条关键词声称解决任意泄漏。对教练评价继续强制引用用户原话。

**验收。** 底牌只在私有资料、未公开引文、无证据评价、NPC 跳出角色分别进入备注字段；公共 UI 均不显示越界内容，正常中性提示保留。

## R7｜预览与最终校验的控制标记规则不一致

**验收。** 标记在完整台词、逐块到达、换行边界、正常引用中均不会变成服务端错误或另一个人物块；最终失败不持久化预览。没有真实模型产生该标记的观察，不能外推线上发生率。

## R11｜知识来源存在，但概念与范围仍要核对

- [`theories.ts:132`](../../app/src/data/corpus/theories.ts#L132) 将“底线”直接解释为“最佳替代方案”。BATNA 是谈不成时的最佳替代行动；底线/保留值是在本次谈判中接受还是退出的阈值，需依据替代方案等因素计算。标题与 howTo 也没有引导用户先列替代行动。可改成“先想清楚谈不成时怎么办，再确定可接受底线”，双语一起修订。[Harvard PON 的定义](https://www.pon.harvard.edu/tag/reservation-price/)明确区分这两项。
- [`theories.ts:268`](../../app/src/data/corpus/theories.ts#L268) 把伴侣冲突讨论中的“三分钟、96%”扩大为“一场对话”的普遍结局。数字本身在 [Gottman 本人讲话](https://edge.org/3rd_culture/gottman05/gottman05_index.html)出现，本轮并不判定它虚构；问题是删掉研究对象和观察语境，标题再写成“决定”。可保留温和开场的做法，将研究作为有限范围的支持，避免让用户以为开场失误就没有修复余地。
- [`theories.ts:506`](../../app/src/data/corpus/theories.ts#L506) 的“改变观点唯一可能的入口”及若干“必然”类表达过于绝对。此项是文案证据强度建议，未逐本核对全部书籍，不能据此判定整库来源失实。

**建议。** 给语料审阅加三项人工核对：概念是否相同、数据适用人群/场景、出处是否支持当前确定程度。有 `source` 字段只是可追溯性的起点。保留框架的实用动作，不把策略变成通用于所有关系的保证。

**验收。** 中英概念一致，研究数字附准确语境/可定位来源，情境失败后仍给修复和拒绝的路；语料结构检查继续通过。

## R12｜模型拟人性与真实设备的验收应补足

当前 273 个测试证明大量结构、边界和确定性行为通过，并不能证明 NPC 始终自然、能记住真实承诺、能辨认玩笑/拒绝/反问，也不能证明有引文的评价含义正确。当前默认 Ling 的新增长程语义验证被共享池阻断，不能引用旧模型回放来宣布它通过。

NPC 精修值得保留的设计是稳定口吻、同一开局的连续记忆、只继承真实记录的反应、有限让步与用户能回应的转折。下一轮应扩充真实盲测，而不是继续堆形容词、固定回合换题或随机刺激事件。

**下一步验证。** 按文字/3D/自定义、中文/英文交叉取样；覆盖让步、拒绝、反问、玩笑、修复、续聊，以及同意与提议的区分。保留原请求、原回复、接受/拒绝原因、实际模型 ID、时延与费用口径，分别记录结构错误、事实错误、剧情断裂、教练改意图和用户体验。不要只存重试后成功样本。

设备侧优先真实 iOS Safari/微信软键盘、输入中断与语音权限、横竖屏/倾斜、长记录/200% 缩放，以及五空间冷加载与稳定帧率。浏览器 390×844 视口不代替实体手机。

本轮主目录搜索、排练草稿刷新、知识展开/关联练习、成长空状态均未复现阻断问题。首次无估计的文案已解释“没有估计不等于能力为零”，不把旧 backlog 空状态建议直接重复判为新 bug。

## R13｜文档、离线恢复和辅助语义整理

1. 架构总览仍写“6 条 LLM 路由”“全部客户端状态在 useApp”“Anthropic 单例”“服务端单进程”，而后面追加章节已描述 OpenAI、独立密钥/3D 键和跨主机共享预算。ModelScope standalone 是单进程，Vercel 不能用同一进程假设。roadmap A24 仍只写 Vercel 已部署。应重写入口摘要与数据流，让最新事实前置，避免继续在文件尾累加互相冲突的说明。
2. “全部 use client 所以原始 HTML 没正文”的旧 backlog 判断不充分；客户端组件标记本身不能据此推断服务端输出。需要区分档案隐私/启动保护与渲染方式，按实际首屏和官网索引目标复核，不能为 SEO 去输出用户档案。
3. 3D 出处说明 [`content.ts:172`](../../app/src/features/dinner/lib/content.ts#L172) 仍称“三个场景/本原型”，实际目录已有五空间；属于中英静态说明漂移，可改为无固定数量的“这些场景”。品牌主句未提出改动。
4. [`sw.js`](../../app/public/sw.js) 只缓存 manifest、icon 和静态 chunks，不提供导航离线回退。浏览器已被 SW 控制时断网刷新 `/3d` 仍到浏览器错误页。README 仅承诺可安装 PWA，未承诺完整离线模型，因此这是恢复体验优化，不能判为已违背离线 AI 功能承诺。可明确联网要求，或增加不生成内容的离线入口以查看/导出已有记录；缓存只接纳成功响应并管理版本。后者已有 backlog，应合并跟踪。
5. 3D 多标签冲突状态的 axe 抽样有一个 minor：[`SaveNotice.tsx:24`](../../app/src/components/SaveNotice.tsx#L24) 的 `<aside role="alert">` 被报角色不适用。可用合适容器保持 alert，测读屏实际播报。14 个对比度节点是 incomplete，不能当作 14 个确定失败。一次抽样也不能声称全站可访问性验收。

这些整理不需要引入新服务或改产品定位。只有 R13 的前三项为维护事实整理；离线属于可选体验改善，辅助语义为有工具定位的小问题。

## 架构判断与修复顺序

**保留。** Next 单应用、浏览器直连个人模型/服务器共享模型的分流、共用任务契约与取消预算、原话校验、场景快照、确定性检索、档案本地保存和独立密钥生命周期，适合当前规模。附件在设备提取、确认文字后发送，匿名统计用严格元数据 schema，方向也与产品约束相符。本轮未证明这些边界失效，但不等于渗透或全面隐私认证。

**收敛。** 应优先统一几条跨模块规则：谁有权写设备键；删除如何让旧窗口失效；哪些模型状态允许生成；哪些模拟字段能进入公共界面；独立练习如何按时间聚合。规则散落在文字/3D/弹窗中，比目录结构本身更容易出错。

**安排。**

1. 先修 R1–R4，取得数据与可用性回归；依赖补丁 R10 同一修订周期处理。
2. 修 R5–R9 和知识概念 R11，加入本轮反例的对应行为验收。
3. 预算可用且有授权的情况下完成 R12 真实模型/设备证据，再集中更新架构摘要与发布说明。

不要扩成微服务，不引入账号/服务端练习库，不为同步独立 3D 演示维护第二套实现。也不建议只因大组件就重构全部 UI；先在有明确行为与回归保护的地方提取保存、模型状态和公开输出边界，再判断 Chat/Debrief 的进一步拆分是否降低实际维护成本。

本报告的总体判定为“需要修订”。四个 P1 有直接复现或线上证据；安全可利用性、任意模型语义与实体手机体验仍缺证据，应保留这些限制。
