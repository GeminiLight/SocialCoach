每周六 14:00（Asia/Shanghai）在当前 Codex 对话产出一次产品迭代提案：回看上轮进展，给出三个候选，推荐一个重点；选定后开发，下一轮验证效果。月度方向沿用现有 B / C / D 路线图。

## 目标与现状

让有一场难谈对话的人完成练习、看懂复盘，并愿意再练一次。持续完善入口、对练、复盘、成长、内容、3D、可靠性与获客，每次只选一个主要问题。

| 已知事实 | 对计划的影响 |
|---|---|
| 已有文字对练、自定义排练、3D、视频观摩、证据式复盘、跨场次模式与本地档案 | 优先复用现有模块，把练习和重练连起来 |
| 10-07 全仓评审仍有跨标签保存、密钥删除、备份恢复等未完成项 | 先复现当前版本；确认仍存在的高优先级问题进入第一轮 |
| 10-08 已提高共享日预算，健康检查与生成资格的提示逻辑仍待修 | 增加额度只能缓解使用受阻，仍需修正提示与恢复路径 |
| 真机、更多模型盲测和线上观测尚未全部完成 | 分开记录代码完成、浏览器验证、真机验证与发布结果 |
| 本次未读取真实用户反馈表或使用统计 | 当前排序来自项目记录，用户需求强度与使用效果均待验证 |

证据入口：[产品提案](../../00-product-proposal.md)、[功能索引](../../01-project-roadmap.md)、[待办与已复现问题](../../85-backlog.md)、[匿名统计边界](../../specs/spec-analytics.md)。

## 每周怎么做

| 步骤 | 产出 | 完成条件 |
|---|---|---|
| 回看上轮 | 已完成、待验证、受阻项与证据链接 | 区分实现、发布和效果；未完成项保留 |
| 找问题 | 用户反馈、行为漏斗、失败记录、试玩观察 | 写出一个具体用户与触发情境；读不到数据时明确标记 |
| 查新信息 | 至多两项相关产品变化或研究发现，附原始来源 | 解释它解决哪个现有问题；外部产品宣传不能当效果证明 |
| 提三个候选 | 问题、证据、最小版本、预计投入、验收、成本与风险 | 查重现有功能和 backlog，注明新功能还是既有改进 |
| 推荐一个重点 | 推荐理由与一个可能推翻判断的证据 | 同时在做的主要功能最多一个；其余留候选 |
| 选定后交付 | 小范围实现、相关回归、试玩与发布记录 | 所需验证通过再按会话已有发布授权推进 |
| 下一轮回看 | 保留、修改、暂停或扩大范围的判断 | 检查用户行为和原话证据，不能只报增加了功能 |

每月最后一次提案同时复查四周结果，删除重复或价值不足的候选，调整下一月重点；候选保留是否由真实反馈支持的标记。

## 如何排序

确认仍存在的数据丢失、隐私失效或核心流程不可用问题优先修复。其他候选依次比较：需求证据强度、对练习闭环的影响、定位契合度、验证成本、长期维护与模型调用成本。小样本阶段使用高 / 中 / 低并说明理由。

优先让用户能开始、完成、看懂和再次练习。3D 扩展每次聚焦一个已有场景的玩法或人物反应，并记录重玩动机；视觉质量与真机性能分别验收。

所有方案沿用项目约束：NPC 保持阻力与信息边界；剧情由行动改变；评价先引用用户原话；知识与案例保留 `source`；练习档案留设备、可导出；静态文案双语；主仓库 `/3d` 为交付主线，独立演示仓库只做低成本可选同步。

## 前四周建议

| 迭代 | 主要问题 | 最小范围 | 验收与后续判断 |
|---|---|---|---|
| 第 1 周：可靠性收口 | 开始不了、提示不准或练习档案丢失会破坏整个体验 | 复现并修复额度状态与生成资格不一致；核对跨标签保存、清除密钥和备份恢复，按严重度分批收口 | 两个正式入口提示与实际生成资格一致；失效时保留草稿并可恢复；已复现的存储反例进入回归。超出一周则继续收口 |
| 第 2 周：关键回合重练 | 复盘指出问题后，重新跑完整场景的成本高 | 先选一个文字单 NPC 场景；用户从一次关键冲突进入短分支练习，练一个动作，如明确拒绝后继续接话 | 分支保留必要前情，原记录完整；NPC 仍可拒绝并回应不同动作；原话来自对应分支。先观察是否主动再次尝试 |
| 第 3 周：前后原话对照 | 用户看见分数，却未必理解自己哪里进步 | 复用已有同场景重练与旧报告，展示两次关键原话及有证据的行为差异 | 校验两场独立记录与引文；区分沟通表现和目标结果；不能比较或未改善时明确说明。观察是否帮助用户选择下一次练习 |
| 第 4 周：一个获客入口 | 有真实急需的人能否找到并完成第一次练习尚待验证 | 从加薪、拒绝额外工作或饭局压力中选一个有反馈支持的主题；复用官网场景页、视频和现有文字 / 3D 入口 | 页面可读、身份与冲突清楚、点击可进入练习；用用户授权的推广渠道观察到达→开始→复盘，不新增整套内容库 |

按每周反馈滚动重排。第 1 周的问题若仍影响体验，则延后新增功能；第 2 周试验若无人主动重练，第 3 周先查原因再扩大。

关键回合重练的状态恢复、场景版本与复盘后信息边界，需要在功能选定后做实现设计。不能保证分支中的 NPC 重复相同台词；已看过底牌的重练也不能算首次盲测。

第 3 周对应既有 backlog 的“同场景前后对照”；第 4 周接续 Stage C / D，已有五个双语官网场景预览可复用。四周投入按能切出一周内验证的最小版本估计，实际开发量尚未评估。

## 后续候选

以下是待验证的产品假设，不代表已确定需求或排期。

| 想法 | 用户得到什么 | 第一步验证 |
|---|---|---|
| 同一冲突的三种压力 | 同一个目标，分别面对追问、关系压力与时间压力 | 用一个已有场景做三种有事实依据的反应，观察是否主动尝试第二种；压力由剧情产生 |
| 现实对话后的本地回访 | 记录实际有没有开口、哪里卡住，再进入相应练习 | 用户自愿记录三项自述，保存在设备；自述不转成模型判定的技能提升 |
| 每周一个动作 | 连续几场只练同一个缺口，例如问清条件或守住边界 | 先复用已有自适应排程，明确本轮练什么；用独立场次原话检查表现变化 |
| 3D 同局不同关系走向 | 让步、拒绝、玩笑和修复改变后续关系与条件 | 一个已有开局覆盖六类回应，观察后果是否可回应，以及是否想重玩 |
| 视频中的关键时刻直接开练 | 看完一个冲突就能试着回应 | 先用现有两条视频与对应场景做一次导航试验，验证用户能否理解情境与身份 |

当前外部参照：Yoodli 官网已展示角色扮演、后续教练与成长测量等能力。因此，“再加一个角色扮演入口”的区分度有限；这是基于其产品展示的判断，优先检验 SocialCoach 的阻力、证据和重练体验。[原始来源](https://yoodli.ai/)（查阅：2026-10-10）。

## 看哪些数

主要结果看“完成一次练习并查看复盘的独立场次数”，同时看七日内再次练习的比例。先核对当前事件是否能正确关联文字、3D、续聊和独立重练，再建立基线。

| 指标 | 口径与用途 |
|---|---|
| 开始率与完成率 | 分母、分子来自同一批设备 / 场次与观察窗口；区分默认模型与 BYOK、文字与 3D |
| 复盘查看率 | 完成后成功显示报告的独立场次 / 已结束且可复盘场次；生成失败单列 |
| 七日再练 | 首次有效练习后的七日内出现另一独立练习的设备比例；队列满七日才比较，按部署分别看 |
| 等待与失败 | 适配、回复、复盘分别观察等待时间和失败类别；有样本量才汇总 P50 / P90 |
| 重练的行为变化 | 两场原话与同难度下的具体动作；模型估计标注为估计，模拟进步不等同现实效果 |
| 体验与成本 | 自愿反馈、现有匿名耗时 / 调用元数据、可读取的实际账单；有成本数据才报告每场费用 |

现有 `retention.ts` 提供按设备首见日的访问复访与后续日期再练统计，与上面的有效练习队列口径不同。先核对事件和时间窗口，不能直接把既有数字改名使用。设备 ID 不等于真人，部署与浏览器之间不合并身份。

小样本周报同时给绝对数与分母；数据不足则用逐场试玩发现提出下一步。可由用户邀请 5–8 位目标用户做探索性试玩，记录卡住的位置与是否主动重练；本计划不授权自动联系他人。匿名统计沿用现有已授权例外，不上传转录或真实处境。

## 每周提案的交付格式

一份短提案包含：上周进展与证据、当前最大问题、三个候选及比较、一个推荐重点及最小范围、下一步验收，以及一项可能推翻推荐的证据。

结果存入 `wiki/reviews/review-YYYY-MM-DD-weekly-product.md`，当轮引用本计划和相关既有 spec。未选定的候选留在周报；选定功能后再写对应 spec / backlog，避免重复扩大任务清单。修改代码前重新读取项目与 `app/AGENTS.md`；保护已有未提交工作，论文及未公开材料不进入产品记录、提交或部署。

本轮仅建立计划与每周提案机制。后续每次提案根据当时的功能与用户证据更新优先级；开发和发布按用户随后选定的范围执行。
