# 3D 饭局剧情连续性复盘

## 现象与原因

1. 第五次开口无法继续：界面、模型提示、请求历史最多 7 条、存档最多 9 条同时写死了四回合。只改界面数字会造成无法请求或无法恢复。
2. 提问还没答就换人换题：离线脚本用回合索引选择台词和演员；物理插曲在第二回合无条件启动。
3. 刚生成的回复被覆盖：动画事件自己的台词优先于最新 NPC 消息，但模型收到的历史不包含这句插话。用户回答的是照片，模型却还在等拒酒的解释。
4. 长记录下错答上一句：第一次重构把 `text` 放在完整历史前，真实模型测试中出现回复上一回合、引用上一句的情况。仅检查 JSON 合法无法发现。
5. 开局事实串线：在共享的家庭事实中同时描述相亲与工作隐私，模型把未发生的工作变动带入相亲线。
6. 台词与动画不符：自由生成的舞台说明会包含吃菜、放筷子等未实现动作。
7. 换开局后切换语言退回旧台词：语言切换调用开场函数时遗漏 variant，标题与台词因此属于不同剧情；统一携带当前 variant，并在正式构建检查中英文来回切换。
8. 现场回复成为大段说明且难以回看：模型上限 650 字与大号居中排版放大了独白，旧复盘又漏掉开场。生成单独限制口语长度，历史与旧存档继续保留原文，不能为了缩短新回复而使旧存档失效。

9. 旁人始终像背景：回复结构只有一位发言人，其他人只能动表情。新增可选同桌短插话，保留为同回合证据；不能靠机械轮流发言模拟群体互动。
10. “草稿在我手机里”却不能查看：原开局只有抽象提示。提供实际可查看的原创开局文案 / 清单，并让模型读到相同资料。明确后续约定以历史为准，不能把开局资料包装为已修改版本。
11. 真实多轮测试发现明确拒绝被转述为待答复、上午复测变成晚间：加强拒绝范围和玩家原话独立证据，限制未知个人信息。98 次真实回复及针对性复测记录在 [沉浸验收](./reviews/review-2026-10-03-3d-immersion.md)；这仍是提示层改进，不是语义正确率证明。

## 修复

- 统一回合预算，默认 12、最多 24；同步请求、持久化、动作时间戳与正文长度；旧四回合记录保留。已达预算的恢复统一为暂停，可手动延长。
- 话题、事实、人物权限和开局独立建模。离线演练按话题 / 历史 / 对话对象响应；模型收到完整历史，最新 `current_player_turn` 单独放最后。
- 模型必须引用当前输入的短片段 `replyTo`；回复人、事件资格、当前原文均校验，失败最多修复一次。仍失败保留草稿，未验证的回复不进入转录。
- 新物理动作只更新动画和动作证据，不再强塞角色台词。后续事件必须由剧情显式引出；拒绝照片后不主动递手机。旧插话按 `heard` 保存，不篡改原话。
- 舞台说明从实际支持的手势生成。不能把模型猜测的动作展示成已发生的现场事实。
- 当前发言最多预览三行，溢出可直接打开完整历史；按开场、双方原话、实际动作重建记录，不用复盘结论替代对话。新生成超限时沿用一次修复预算，禁止硬截断拒绝或条件。见 [对话区验收](./reviews/review-2026-10-03-3d-conversation-ui.md)。

## 验证与局限

自动检查覆盖长对话边界、旧存档、指定对象、事实隔离、拒绝后的事件、修复上限与真实动作。三桌各 12 回合的真实模型转录另外人工阅读，脚本为 `app/scripts/check-dinner-story-live.ts`，只使用合成用户发言。

结构正确、当前引文存在，不等于语义永远正确。NPC 对其他人的表态仍可能误读；完整上下文让用户可以继续追问和纠正，但要继续扩大自然输入盲测。离线演练明确标识为能力有限的内置模式，不宣传为任意情境理解。

通用教训：验证真实用户看到的对话顺序；长对话至少跑到上限以后；把当前消息与已答历史分开。不要用回合号代替剧情因果，也不要用固定插曲替用户定义话题。

Skill evolution: no update needed。现有 fix-bug 流程已经要求完整复现与真实路径验证，本轮问题与预防措施记录在项目内。

## 沉浸动作与对话的时间边界

模型请求中的 `busy` 不能同时意味着整桌静止。之前把请求等待传给场景暂停，人物连眨眼 / 呼吸都冻结；长时间组织语言时，动作时间也冻结，杯子悬在半空。现在等待保留独立环境动作和探索，视觉动作自然走完，真正面板暂停与隐藏标签页单独处理。动作结束不自动同意、不消耗回合。普通模型手势和物理举杯均需检查放下后的桌面杯子，避免双份物件或永久缺杯。

## 条件式剧情与多轮事实（2026-10-04）

实际回放又出现：office-interruption 把另一开局 18:30 期限带进来；权限待核被说成无权访问；讨论排版被记成接了排版；模型把 decision / priority 同时写进 topic / beat；敬茶正常回答带重复开场举杯而被整句退回。共用角色、长历史与结构正确都不能自动防这些问题。

处理：十开局按自己的事实 / 人物动机提供条件式机会，beat 随原话进入下一次 payload；过去 / 未来提议 / 同意 / 已完成分别提示。已复现的少数无依据事实经狭义 guard 走已有修复。重复动作与有效 beat 误放 topic 属于内部元信息冗余：本地规范化后仍校验原话、人物、长度、未知事件等，不把所有失败一律交给更慢的模型重跑。

一个旧检查曾要求“当前动作重复请求必须失败”；新的预期是移除重复 event、不重放、保留正常台词。同步改检查并保留外来动作 / 未出现动作仍失败的反例，不能只删断言变绿。172 项检查与完整回放见 [评审](./reviews/review-2026-10-04-scene-craft.md)。

教训：应对模型元信息混淆和应对内容造假需要不同处理。有效 spoken answer 不该因无意义的重复动画等待重试；陌生事实也不能通过去掉字段自动变成可信台词。正则和提示没有解决通用语义，文字仍可误记时间，后续盲测继续保留原始失败样本。
