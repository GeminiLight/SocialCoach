# 复盘追问：有原话不等于解释正确

2026-10-22，真实模型六轮文字 / 3D 对练后发现。产品验收原件见 [live-workflow-2026-10-22](../docs/reviews/live-workflow-2026-10-22/)，不含真实用户、凭证或论文材料。

## 现象与原因

1. 复盘助手引用了真实原话和合法来源，却在 `answer` 里写新的示范台词；“延迟时可以通知”变成“保证提前通知”，“只愿意列问题”变成“今天发给你”。旧任务只校验字面引用、来源白名单和 JSON 形状，没有在交付前核对解释、承诺范围与示范。
2. 对话前段的“谁来核实”覆盖了后段 NPC 的“我自己去看来源”，把已提出的责任归属继续写成无人承担。引用本身可以完全正确，结论仍与完整时间线相悖。
3. 模型把短回答拆成四段，旧 schema 的三段限制拒绝了本可安全合并的文本。外部接口本来只交付一个有长度上限的字符串。
4. 加入独立核对后，四次调用的修复链有实际 55 秒超时。客户端、任务与路由必须一起调整，不能仅延长其中一层。

## 修复

- `checkDebriefReply()` 在展示前独立读取公共场景、完整转录、实际来源和草稿，核对新示范的位置、说话人、后续责任归属、承诺与完成状态。反思和追问共用；引文与来源白名单仍先行执行。
- 明确引导的新引用台词先由字面检查拦截：实际转录引用保留，新示范即使被模型批准也不能混入 answer。
- 最多一次重新生成，并再次核对；未通过、核对输出无效或取消均不交付草稿。不以自动替换原话、删掉问题句或放宽证据规则制造成功。
- 生成提示收窄为简短解释；只问已发生 / 已约定事实时不额外追加示范和新计划；反思只回应本次自述，避免擅自代写交接方案。示范自身必须保留条件，正文的免责声明不能为示范里的无条件承诺兜底。
- 短段落可合并，answer 总长仍不超过 3600 字符，example 总长不超过 1200 字符。示范的一项短数组同样做无损合并，随后仍须通过内容核对；现有 string 响应不变。
- 反思与追问仍最多四次调用，任务上限 85 秒，路由上限 90 秒；追问 UI 直接读取共享任务上限。增加一次常规核对的调用成本，换取交付前的证据审核；用户可随时停止。

## 验证与边界

保留了失败草稿、核对结论、修复尝试和最终记录。中英文新增承诺反例，以及中文遗漏后续责任归属反例，均用真实模型重新核对；确定性测试覆盖有真实引文但语义被拒、修复后再次检查、核对结果损坏、取消和总长度。

这是防线加强，不是自然语言解释永远正确的证明。初版核对仍放过过新增承诺和旧责任状态，随后用真实反例补足检查规则；这些失败没有被删除或计为成功。模型校验仍可能漏报或拒绝合理措辞，达不到标准时保留用户记录并允许重试。更广泛的模型与场景盲评继续列在 backlog，不能用本轮四个样本替代。
