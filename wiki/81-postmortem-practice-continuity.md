# 练习连续性复盘

2026-10-01 至 10-02 的本地回归确认了 `Chat` 的三个相关问题：流中断保存半截 NPC 回复；刷新 / 暂停后未完成发言失去恢复入口；最后回合阅读停顿仍可输入。关联问题还有准备失败绕过适配、重复复盘累加能力，以及档案读取失败空白。复现与证据见 [第二轮评审](./reviews/review-2026-10-01-practice-recovery.md)。

## 根因

原来的回复增量直接调用 `updateLastNpc`，把正在生成的预览当成了完整转录。流尾发生错误时记录已经落盘，重试只删除空 NPC 消息，留下非空的半截内容；复盘也可能将它视为真实台词。

错误、请求与结束停顿只存在于组件内，没有与持久化的场次状态共同决定允许哪些操作。刷新丢失错误状态；离开不会取消请求；设置 ending 只影响提示，未封住输入动作。三个问题都源于把“正在进行”和“已经完成”混在同一条路径里。

`applyReport` 也缺少状态前置条件。同一份报告或迟到的报告可以再次改变能力与完成日期。与此同时，persist 失败回调不一定获得 state，原来的 `state?.setHydrated()` 永远无法解除空白等待。

## 修复边界

1. 临时流在组件内展示；响应完整且无错误后，台词与目标 / 立场 / 收尾一次写入。错误流不会贡献复盘证据。
2. 从最后一条非教练记录推断未完成交互，刷新后保留恢复路径。重试移回原话，不自动重复提交。暂停与结束取消请求和计时器，迟到结果不能写入。
3. 结束条件锁定界面和动作；刷新时根据已完成回复、closure、回合或沉默上限继续结束流程。
4. 复盘只允许 ended 且无报告的场次进入 assessed。相同报告、删除场次和仍在练习中的场次不更新能力 / 日期。
5. 读取失败先保护原始字节，再显示恢复页。没有静默重置；用户可下载原文、重试读取，备份动作后才能显式确认清空。

没有改变 API 协议、模型的 NPC 阻力要求、持久化 schema、评分规则或来源约束。也没有把任意合法 JSON 的 schema 校验、写盘配额错误、跨标签页协调或导入合并纳入已完成范围。

## 防回归

`check-practice-recovery.ts` 检查准备失败、错误流、原话重试、刷新恢复、结束窗口、临时预览以及离开后的迟到回复。`check-store-recovery.ts` 同时覆盖语法损坏与访问拒绝，验证原文不被初始化 / 语言切换覆盖，以及报告仅应用一次。`check-storage-recovery.ts` 检查恢复页双语明暗布局、可访问性、原样备份和取消 / 确认重置。

以后改流式交互时，同时验证正常完成、部分完成后错误、刷新、离开、重复操作与迟到完成。检查的是状态和真实记录，不只检查有没有错误提示。可见预览、持久化转录和复盘证据必须保持各自的完成条件。
